## ASAR format notes (verified on this bundle)

- Nativev2 header: `[u32 @0]=4`, `[u32 @4]=header+8`, `[u32 @8]=header+4`,
  `[u32 @12]=header JSON length` (3 113 800), JSON begins at offset 16.
- `header.files` is the root container (name → child) — children must be
  walked directly.
- **Offsets are relative to the data section start (`16 + headerSize`), not
  absolute.** Reading them as absolute yields garbage (verified:
  `package.json` at absolute `228994818` was binary noise; relative read gives
  valid JSON). The repo tool auto-detects this.

## Request shape (from the 2.2.5 binary + live capture)

Headers:
- `x-opencode-session` / `x-opencode-session-id` / `x-session-affinity` /
  `X-Session-Id` → same session id (`ses_` + 12 hex inverted-ms + 14 base62)
- `x-opencode-parent-session-id` / `x-parent-session-id` (when parented)
- `x-opencode-project` (40 hex, sha256 of project identity)
- `x-opencode-client` (`cli` / `desktop`)
- `x-opencode-directory` (URI-encoded working directory)
- `x-opencode-org-id` (org metadata, billed flows)
- `User-Agent` = `opencode/latest/<version>/cli` (via `Yd`)

Body (chat):
- `model`, `system`, `messages`, `tools` (`[{type:"function",function:{...}}]`),
  `toolChoice`, `generation` (subset of `hh.fields`), `providerOptions`,
  `cache`, `promptCacheKey` (`ses_…` trimmed of `ses_` when 64-hex),
  `stream`, `stream_options` (`{include_usage:true}`)
- The client's own tool **registry** in the binary is `shell, glob, read,
  grep, webfetch, websearch, write, edit, subagent, execute, patch,
  todowrite, question, skill` (14 ids — `UPt` set). But a **real 2.2.0
  dispatch sends only 11** in this order: `edit, glob, grep, read, shell,
  skill, subagent, webfetch, websearch, write, execute` — each with the
  client's own description/parameters and `strict:false`. No `patch`,
  `question`, or `todowrite` (see the live capture below).

## Cross-reference: opencode2api bridge + SDK 1.19.0

- The public `opencode2api` bridge (v2.5.0) is a proxy to a **local** OpenCode
  1.x server (`OPENCODE_SERVER_URL`), speaking the SDK API (`/session`,
  `/session/{id}/prompt`) with `Basic` auth — it rejects backend 2.x, so it is
  NOT an example of the cloud `/inference` wire.
- Its comment (proxy.js ~1522): "OpenCode Zen's free tier rejects any request
  whose tool list differs from the official client's ('free tier can only be
  used from within OpenCode')".
- SDK 1.19.0 v2 types: `PromptInput = {text, files?, agents?}`,
  `ModelRef = {id, providerID, variant?}`, `ToolListItem = {id, description,
  parameters}`; `tool/list` = `GET /experimental/tool?directory&workspace&provider&model`
  (server-local only; 404 on cloud `/inference`).

## Anonymous `Bearer public` sentinel — verified live

Replaying the same captured free-tier chat flow with three auth variants
(2026-11-02, `glm-5.3-flash-free`) all answered **200 `text/event-stream`**:

- `Authorization: Bearer public` (the anonymous sentinel) → 200 SSE
- no `Authorization` header at all → 200 SSE
- `Authorization: Bearer st_…` (the real account token) → 200 SSE

So the free-tier gate accepts the anonymous `public` sentinel (and even an
absent Authorization) as long as the body/fingerprint is valid; the sentinel
is not a secret and does not need to be replaced with an account token. The
earlier `429 FreeUsageLimitError` was quota/cooldown state, not an auth or
wire-shape refusal — the identical flow answered 429 while the quota was
exhausted and 200 once it recovered. (Full detail in
[`2026-11-02-opencode-free-tier.md`](./2026-11-02-opencode-free-tier.md).)
